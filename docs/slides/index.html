1. 문제 배경

외부 공급망 충격이 제조 스케줄링에 미치는 영향

  • 2026 호르무즈 해협 봉쇄 — 해상 석유 교역량 20% 차단, 운송 기간 최대 2주 연장
  • 제조업: 단일 핵심 부품 입고 지연만으로도 조립 라인 전체 중단
  • 고정 dispatching rule (FIFO/EDD/SPT/CR)은 외부 충격의 강도·형태가 변할 때 동적 대응 한계
  • FJSSP의 구조적 가능성: 동일 공정을 여러 기계에서 처리 → 부품 지연 작업 우회 가능
충격 강도·형태에 따라 변수 중요도가 동적으로 바뀌는 환경에서, LLM이 dispatching rule을 자동 생성·진화시킬 수 있는지 정량 검증.
📝 부가 설명
  • 호르무즈 사례: 2026년 외부 공급망 충격이 제조 라인에 미치는 영향을 보여주는 대표적 사건. 단일 부품 지연 → 라인 전체 정지로 이어지는 cascade 효과.
  • Dispatching rule: "어느 작업을 어느 기계에 다음 처리할지" 결정하는 규칙. 매 머신이 비는 순간 호출됨.
  • JSP vs FJSSP 차이: JSP는 각 공정이 한 기계에 고정 (M3에서만 처리 가능), FJSSP는 여러 기계 중 선택 가능 (M1·M3·M5 중). 후자가 외란 대응에 유리.
  • 왜 LLM인가: 인간이 수동으로 규칙 설계 시 변수가 늘수록 조합 폭발. LLM은 자연어 → 코드 변환으로 변수 결합 다양성 탐색 가능.

2. 연구 질문

RQ1

LLM이 진화시킨 규칙이 12종 인간 baseline 중 가장 강한 것을 AT 기준으로 이길 수 있는가?

RQ2

LLM에게 외부 충격 변수(part_available_time, urgent_order_flag)를 노출하면 성능이 개선되는가?

RQ3

같은 시나리오 내 성공·실패 경험 memory를 누적·재활용하는 것이 추가 기여를 갖는가?

핵심 metric: AT = (1/n) · Σ max(0, C_j − d_j) · 부지표 MIT(machine idle) · PTJ(tardy %) · ARI(vs best baseline; 양수 = LLM 우위)
📝 부가 설명 — 지표 정의
  • AT (Average Tardiness): 평균 납기 초과량. C_j = 작업 j 완료 시각, d_j = 납기. max(0, ...)는 일찍 끝나면 0 (early bonus 없음). 작을수록 좋음.
  • MIT (Machine Idle Time): 머신이 "할 일 없어 놀고 있던" 총 시간. 모든 머신 합산. 작을수록 효율적이지만 AT와 같이 봐야 의미 있음.
  • PTJ (Percentage of Tardy Jobs): 납기 어긴 작업의 비율 (%). AT가 같아도 "소수가 크게 늦었나(낮은 PTJ) / 많은 작업이 조금씩 늦었나(높은 PTJ)" 구분.
  • ARI (Average Relative Improvement): (AT_baseline − AT_proposed) / AT_baseline × 100. spec §8 부호: 양수면 LLM이 우위.

3. 접근

LLM 듀얼 에이전트 + EoH 진화 루프

아키텍처

  • LLM-A (Generator): 우선순위 함수 코드 생성
  • LLM-S (Reflector): 성공·실패 추출 → 메모리
  • 모델: gpt-4o-mini (둘 다)

진화 연산 (EoH §4-4)

  • Explore · Crossover · Modify · Simplify

진화 루프 1회 (pseudo)

population = B1~B5 + LLM_init(5)   # 10개
for it in 20 iterations:
    scores = simulate(pop, scenario, 100 reps)
    elite  = top_3(pop, scores)
    if P3:
        mem += LLM_S.reflect(success, failure)
    new    = LLM_A.{explore, crossover,
                    modify, simplify}(elite, mem)
    pop    = elite + new

Fitness = 순수 AT (= 페이퍼 §8 primary metric)

📝 부가 설명 — 듀얼 에이전트의 의의
  • LLM-A와 LLM-S 분리 이유: 한 LLM이 generator + reflector 다 하면 confirmation bias 위험. EvoDR(Qiu 2026)이 분리 권장. 본 실험에선 같은 모델 인스턴스 공유 (system prompt만 다름) — 그러나 호출 단위는 분리됨.
  • Elite (top 3): AT 가장 낮은 3개를 다음 iter에 그대로 보존. elitism으로 최고 성능 유지하면서 새 6개로 다양성 확보.
  • 왜 fitness = pure AT: 이전엔 composite (tardiness + 0.5×makespan + ...)이었는데 spec §8과 불일치. v3에서 모든 비-AT 가중치 0으로 → fitness ≡ 평가 metric.
  • EoH (Evolution of Heuristics, Liu 2024 ICML): explore/crossover/modify/simplify 4 연산이 표준. 본 실험도 그대로 차용.

5. 외부 충격 시나리오

실험설계서_수정 §4 — 단일 변수 통제로 효과 분리

시나리오설명본 실험 설정
S0 정상외부 충격 없음. 베이스라인 reference—
S1 부품 지연 시뮬 도중 head op의 part_available_time이 미래로 갱신.
Uniform(0.1~0.3·T_est) 시각, 영향비율 ratio%		 ratio=20%, k=1.0
S2 긴급 주문 시뮬 도중 새 urgent 작업 1개 삽입.
Uniform(0.2~0.5·T_est), 기존 라우팅 복제		 납기계수=0.3 (tight)

스펙 §4-3 3수준 {0.3, 0.5, 1.0} 중 가장 tight한 0.3으로 진행 — S2 베이스라인 격차가 더 분명하게 나오도록.

📝 부가 설명 — 시나리오 파라미터 의미
  • T_est (trivial makespan lower bound): max(각 작업의 총 처리시간). 시뮬 길이의 보수적 추정치. S1·S2의 onset 시점 결정에 사용.
  • S1 ratio (영향 비율): 0.20 = 12 작업 중 약 2~3개의 첫 공정 부품이 늦어짐. 0.10은 너무 약함, 0.40은 시스템 마비 가까움.
  • S1 k (지연 계수): 평균 총 처리시간 × k 만큼 늦어짐. k=1.0이면 정확히 평균 처리시간만큼 → 의미 있는 충격이지만 회복 가능.
  • S2 납기계수: 새 긴급 작업의 due = release + ratio × 평균_총_처리시간. 0.3은 매우 빡빡 → 사실상 달성 어려움. spec이 "물리적으로 달성 어려운" 수준이라 명시.
  • S2 긴급 작업 수 = 1 고정: spec이 "여러 개면 결과 해석 복잡"이라며 1로 강제. 본 실험도 이를 따름.
  • 발생 시점 Uniform(...): random하게 시점 선택 — 시드별로 다른 인스턴스. 100 seed 평균이 generalization 보장.

6. P1 / P2 / P3 변형

LLM에게 무엇을 보여줄지의 차이 — RQ2·RQ3 직접 검증

변형LLM이 보는 변수메모리측정 의도
P1 기본만 (release_time, due_date, processing_time, remaining_pt, machine_id…) 없음 외부 충격 모르고도 휴리스틱 어디까지
P2 + urgent_order_flag, part_available_time 없음 충격 인지 자체의 가치
P3 + 충격 변수 있음 (top-K lesson) 경험 축적의 추가 가치
📝 부가 설명 — 변수 정의
  • disruption 변수 (P1이 숨기는 것): urgent_order_flag (S2 marker), part_available_time (S1 marker). 이 둘이 외란을 감지할 신호.
  • 모든 변형이 공통으로 보는 변수: release_time, due_date, remaining_pt, processing_time, machine_id, machine_available_time, current_time, eligible_machines — 정상 스케줄링에 필요한 기본 변수.
  • P3 메모리 = top-K lesson 누적: success/failure 패턴이 매 iter prompt에 주입. K=3 (top-3 retrieval).
  • 왜 P1 ↔ P2 ↔ P3 단계적: 정보를 한 차원씩 추가하면서 각 차원의 marginal contribution 분리 측정. 모두 한 번에 주면 어느 게 효과인지 모름.

7. 베이스라인 12종

1950~2000 문헌 표준 + 보고서 §5-1

B1~B5 (보고서 §5-1)

  • FIFO · EDD · SPT · CR · Urgency

→ LLM 초기 population에 포함

문헌 추가 7종

  • WMDD, COVERT, ATC, MDD, MWKR, LWKR, LPT

→ 외부 비교 대상으로만 사용 (LLM은 못 봄)

벤치마크 의의: 페이퍼들이 보통 B1~B5만 비교 → 우리는 12종 통틀어 가장 강한 것 vs LLM. paper-favorable 비교 회피.

📝 부가 설명 — 12 baseline 각각 한 줄
ID이름규칙 (직관)강점
B1FIFO도착 순서대로 처리단순. 납기·처리시간 무시.
B2EDD납기 빠른 작업 먼저 (Earliest Due Date)납기 압박에 강함
B3SPT처리시간 짧은 것 먼저 (Shortest Processing Time)makespan ↓, 머신 회전 빠름. strict JSSP 최강.
B4CRCritical Ratio — slack/remaining_pt 작은 것시간 압박 + 남은 일 균형
B5Urgencyurgent=1 작업 우선 가산단순한 외란 인지
—WMDDmax(due, now+proc) / penalty 최소화 (Eilon 1976)FJSSP 환경 최강 baseline
—MDDWMDD의 무가중 버전 (Baker-Bertrand 1982)WMDD와 유사 성능
—COVERTpenalty/proc × max(0, 1−slack/proc) (Carroll 1965)시간 압박 + 페널티 결합
—ATCpenalty/proc × exp(−slack/k·proc) (Vepsalainen-Morton 1987)exponential soft-threshold
—MWKR남은 일 많은 것 우선 (Most Work Remaining)긴 작업 일찍 시작 — AT엔 약함
—LWKR남은 일 적은 것 우선 (= SRPT 변형)flow time ↓에 좋음

발표 시 핵심: WMDD·MDD·CR·EDD가 FJSSP 환경에서 SPT보다 강력 — LLM이 이것들을 넘기 어려운 게 본 실험 baseline 격차 작은 이유.

8. 진화 루프 상세 — 한 iteration 안에서

단계별 흐름

  1. 평가: 10 expr × 100 seed 시뮬레이션, 평균 AT 산출
  2. Elite 선정: top 3 (AT 오름차순)
  3. (P3) Judge: best baseline AT × 0.95 ↘ → success, × 1.05 ↗ → failure
  4. (P3) Reflect: LLM-S가 success/failure 보고 lesson 추출 → MemoryBank
  5. 생성: LLM-A가 4 연산 × 6 호출로 새 expr 6개
    (explore×2, crossover×2, modify×1, simplify×1)
  6. Population 갱신: elite 3 + new 6 = 9 (다음 iter)

한 iter 비용 추정

단계호출수시간
시뮬레이션10×100=1000~2초
LLM-A 호출6~18초
LLM-S 호출 (P3)1~3초
한 iter 합—~23초
20 iter / combo—~8분
9 combo 병렬—~9분 wall

시뮬레이션은 Rust binary로 위임 — LLM은 절대 시뮬 안 함. AT 평가는 결정론적·신뢰 가능.

📝 부가 설명 — 한 iter 안의 6단계
  • cache 역할: 같은 expression이 이전 iter에서 평가됐으면 시뮬 다시 안 함. 진화 후반 elite가 거의 같은 expr이라 cache hit ratio 50~70%.
  • "AT × 0.95/1.05": success/failure 임계값. baseline 대비 5% 이상 좋아지면 success, 5% 이상 나빠지면 failure. 그 사이는 noise라 보고 메모리 안 들어감.
  • 왜 population 갱신이 3+6=9 (10이 아니라): 코드 작은 결함 — spec은 10 유지를 의도했을 수도. 큰 영향 없음 (사실상 elite + 6 새로 만든 거).
  • 병렬 한도: gpt-4o-mini Tier 1 = 500 RPM / 200K TPM. 9 combo 병렬 시 약 130 RPM 사용 (26%) — 한도 안.

9. 진화 연산자 4종 — LLM-A가 호출되는 방식

같은 LLM-A에 task description만 바꿔서 4가지 모드로 사용 (iter당 6 호출: explore×2, crossover×2, modify×1, simplify×1)

① Explore (탐색)

기존 elite와 구조적으로 다른 새 expr 생성

Task:
explore - Generate a NEW priority expression
structurally distinct from the elite below.
  - AT=158.6  expr: -(due_date - current_time) - 0.5*processing_time
  - AT=170.2  expr: 0.0 - due_date

응답:

Code: exp_(-max_(0, due_date - (current_time + remaining_pt)))
       - 0.1 * processing_time

② Crossover (결합)

상위 2 elite의 강점 합치기

Task:
crossover - Combine these two top expressions:
  A: exp_(-max_(0, due_date - (current_time + remaining_pt)))
  B: -(due_date - current_time) - 0.5 * processing_time

응답:

Code: 0.7 * exp_(-max_(0, due_date - (current_time + remaining_pt)))
       - 0.3 * (due_date - current_time)
📝 부가 설명 — Explore / Crossover
  • Explore가 가장 다양성 ↑: elite를 reference로만 보여주고 "다르게 짜라" 요청. 가장 큰 발견 가능성이 있지만 실패도 잦음.
  • Crossover의 가중치 0.7/0.3: LLM이 임의로 선택. 단순 가산부터 함수형 결합까지 다양. 매 호출마다 다른 가중치 시도.
  • 왜 explore × 2: 한 번이면 운에 의존, 두 번이면 안전. modify·simplify는 점진적이라 1번씩.
  • LLM 응답의 Thought 필드: LLM이 자기 판단의 근거를 자연어로 적음. 우리는 Code만 사용하지만 Thought는 디버깅 시 LLM의 추론 추적에 유용.

10. 진화 연산자 — Modify / Simplify

elite의 구조를 유지하면서 가중치 튜닝 또는 항 제거

③ Modify (수정)

top elite의 구조 그대로, 가중치·임계값만 튜닝

Task:
modify - Tune weights or thresholds of this
expression; keep its structure.
  base: -(due_date - current_time)
        - 0.5 * processing_time

응답 (계수만 변화):

Code: -1.5 * (due_date - current_time)
       - 0.3 * processing_time

④ Simplify (단순화)

기여 작은 항 제거 → 더 간결한 식으로 일반화

Task:
simplify - Remove terms that do not pull their
weight; produce a simpler expression.
  base: -1.5 * (due_date - current_time)
        - 0.3 * processing_time
        + 0.1 * urgent_order_flag

응답 (마지막 항 제거):

Code: -1.5 * (due_date - current_time)
       - 0.3 * processing_time
4 연산자가 만드는 균형: explore (다양성) ↔ crossover (좋은 구조 결합) ↔ modify (fine-tune) ↔ simplify (일반화). EoH (Liu et al. ICML 2024) 원형 따름.
📝 부가 설명 — Modify / Simplify
  • Modify가 가장 안전한 개선: 구조 유지하니까 망가질 위험 작음. fine-tuning 단계에서 가장 자주 best 갱신.
  • Simplify의 의의: 진화 후반에 식이 점점 복잡해지는 경향 → simplify가 occam's razor 역할. 같은 성능이면 단순한 게 일반화↑.
  • Modify ≠ random mutation: 임의로 가중치 흔드는 게 아니라, LLM이 "왜 그 가중치가 더 좋을지" 판단해서 변경. EvoDR 방식.
  • EoH의 핵심: 사람의 GP(Genetic Programming)에서는 mutation을 무작위로 했음. LLM 도입으로 "의미 있는 mutation" 가능 — 이게 핵심 차별점.

11. LLM-S 작동 — Judge → Reflect → Memory

P3에서만 호출. 평가 끝난 직후, 다음 iter 생성 전.

Step A: LLM-as-judge 분류 (코드)

lo = baseline_score * 0.95   # 5% 더 좋은 기준
hi = baseline_score * 1.05   # 5% 더 나쁜 기준
for r in results:
    if r.at <= lo:  successes.append(r)
    elif r.at >= hi: failures.append(r)
    # 그 사이 = neutral, 메모리에 안 들어감

예: WMDD baseline AT=57일 때, AT ≤ 54.15 = success, AT ≥ 59.85 = failure.

Step B: LLM-S에게 가는 prompt

Scenario: S1

SUCCESS rules:
- AT=51.4  expr: exp_(-0.125 * max_(0, due_date -
  (current_time + remaining_pt + part_available_time))) / remaining_pt
- AT=53.0  expr: -(due_date - current_time) - 0.5 * processing_time

FAILURE rules:
- AT=82.5  expr: 0.0 - release_time
- AT=99.7  expr: processing_time

Write 2 to 4 lessons in this exact format:
LESSON: ... END

Step C: LLM-S 응답 (실제 추출 예)

LESSON:
type: success
title: Weight slack heavily over processing time
description: S1 part-delay with moderate intensity
content: Linear combination -1·slack - 0.5·proc beats either
alone — slack carries due-date signal, proc handles machine
turnover.
perf_delta: -9.7
END

LESSON:
type: failure
title: Single-variable rules ignore critical signals
description: Any disruption scenario
content: Pure -release_time or processing_time ignores due
dates AND processing simultaneously.
perf_delta: +18.5
END

LESSON:
type: strategy
title: Combine slack with /remaining_pt normalisation
description: When work-content varies across jobs
content: Dividing by remaining_pt normalises priority across
job sizes; raw subtraction overweights long jobs.
perf_delta: 0
END

정규식으로 LESSON 블록 파싱 → MemoryItem dataclass로 저장.

📝 부가 설명 — LLM-S 작동
  • 왜 LLM-S를 분리: LLM-A가 동시에 generator + reflector면 자기가 만든 걸 자기가 평가 → 편향. 별도 호출로 객관성 확보 (같은 모델 인스턴스라도 prompt 분리로 충분).
  • 5% threshold 의미: 노이즈(stddev/√100 ≈ 1~2%)보다 큼. spec §5-3 명시값. 너무 작으면(1%) 노이즈가 lesson에 들어가고, 너무 크면(20%) lesson이 거의 안 쌓임.
  • perf_delta 부호: success는 음수 (baseline 대비 AT 작음), failure는 양수 (AT 큼). LLM-S가 직접 채워넣음 — 자기가 본 데이터 기반.
  • LESSON 형식 위반 시: 정규식 매치 0건 → 이번 iter엔 메모리 추가 0건. 다음 iter LLM-S가 다시 시도. silent fail.

strict (flex=0)

  • SPT 절대 강자
  • routing 결정 없음 → 처리시간만이 유일한 핸들

  • WMDD/MDD/CR/EDD 강자

  • LLM도 같은 영역에서 새 규칙 탐색
📝 부가 설명 — 강자 변화의 의미
  • strict JSSP에서 SPT 절대강자: 처리시간이 유일한 자유 변수. 짧은 거 빨리 해치우면 머신 회전 빠름 → AT 최소.
  • FJSSP에서 SPT 6위로 떨어짐: routing이 짧은 작업을 빠른 머신에 자동 배치 → 처리시간 차이가 흡수됨. 대신 due_date 기반 규칙이 더 중요.
  • WMDD (Weighted Modified Due Date): max(due, now+proc)/penalty. 늦을 작업에 더 큰 페널티 부여 — FJSSP에서 가장 효과적인 인간 규칙.
  • 발표 시 핵심: "어떤 규칙이 좋은지는 환경에 따라 다르다" → 정적 규칙 한계 → LLM의 적응적 진화가 의미 있음.

tardy 작업에 지수적 가중 + urgent OR "막 도착한 작업" 미세 boost — EDD의 부드러운 일반화

📝 부가 설명 — LLM 표현 해석
  • evalexpr DSL 한 줄 표현: 모든 LLM 출력은 단일 수식. higher score = higher priority. 머신이 빌 때 후보들에 적용해 최고 점수 작업 선택.
  • exp_(-max(0, X)): X > 0이면 지수적 감쇠, X ≤ 0이면 1. "tardy 작업일수록 우선" 같은 부드러운 페널티에 자주 등장.
  • strict (flex=0.0) 표현이 SPT 닮은꼴: routing 결정 없으니 처리시간 중심. urgent boost가 1000 같이 큰 값 곱셈 — sharp priority.
  • FJSSP (flex≥0.5) 표현이 due_date 중심: routing이 처리시간 효과 흡수 → due가 차별화 기준. LLM도 자연스럽게 이 방향으로 진화.

RQ2 / RQ3 답

  • RQ2 (충격 변수 효과): S0/S1에서 P2>P1 — 변수 노출 자체로 효과 있음
  • RQ3 (메모리 효과): S1에서 P3≈P2 (memory 추가 효과 거의 0), 다른 cell들에선 작거나 음수
  • S2 limitation: 단일 긴급 케이스로 변형 차별 안 됨 → multi-urgent로 후속 검증 필요
P3의 메모리 효과가 우리 예상보다 작음. 이유: 한 시나리오 안에서 lesson이 빠르게 saturate → 새 lesson이 기여하는 marginal 정보가 적음. cross-scenario memory나 longer evolution이 효과를 키울 가능성.
📝 부가 설명 — RQ 답
  • RQ2 답: "충격 변수 노출이 가치 있다, 단 환경에 따라 다르다." S0/S1에서 P2 > P1 명확, S2는 saturate라 측정 불가.
  • RQ3 답: "메모리 효과는 우리 setup에선 marginal." 같은 시나리오만 사용하니 lesson saturate. cross-scenario memory가 진짜 효과를 보일 가능성 (TODO).
  • "meaningful improvement" 기준: stddev/√100 ≈ 1~1.5. 3+ 차이는 안전한 win. 1~2는 noise 의심.
  • 발표 시 약점 인정 framing: "P3 효과가 명확치 않은 건 시나리오 다양성 부족 때문이라 생각. 다음 단계 실험으로 검증 계획" — 솔직하면 신뢰 ↑.

21. 정직한 평가

thesis와 데이터의 정렬·괴리

✓ thesis와 정렬

  • FJSSP가 AT 감소의 주요 동력 (flex 0→1: 65~80% ↓)
  • flex≥0.5 + S0/S1에서 LLM이 일관되게 baseline 우위
  • 최강 baseline이 flex에 따라 바뀜 — routing 자유도가 metric 지형 변화
  • 변수 노출 (P1→P2) 가치 명확 (S0/S1)

✗ thesis와 어긋남

  • LLM ARI peak이 flex=1.0이 아니라 flex=0.5 — full FJSSP는 baseline도 거의 최적
  • S2가 saturate — 단일 긴급 작업에선 WMDD가 본질적으로 최적, LLM 여지 없음
  • 메모리(P3) 효과가 작음 — 짧은 진화 + 좁은 시나리오
해석 framing: "LLM이 빛나는 영역은 moderate FJSSP × 비단순 disruption" — 너무 자유롭거나 너무 단순한 양 극단에서는 baseline이 충분. 이게 정직한 페이퍼 결론.
📝 부가 설명 — Q&A 방어
  • "thesis와 어긋난 부분이 있는데 페이퍼 의미 있나?": 어긋난 부분이 새로운 발견 — "flex=1.0에서 LLM이 못 빛난다"가 자체로 finding. negative finding도 paper contribution.
  • "왜 LLM이 flex=1.0에서 약한가?": routing이 너무 자유로워 단순 EDD/CR도 거의 최적 → LLM 추가 기여 영역이 작음. 이게 직관적 해석.
  • "S2 saturate가 메서드 결함 아닌가?": spec이 "긴급 1개 고정"이라 strict하게 따른 것. 다중 긴급은 spec deviation으로 TODO에 명시.
  • "메모리(P3) 효과 작은데 P3 의미 있나?": marginal하지만 일관 양수. 또한 cross-scenario memory가 진짜 효과 영역. 이번 setup의 한계 인정.

25. 현재 고민 — 방향성 결정 필요

지도교수님 자문 요청 사항

외부 충격 변수를 dispatching rule에 노출 → LLM이 활용해서 진화 — 이 방향까지 진행 완료.
이제 세 갈래의 선택지가 있고 어디로 갈지 결정 필요.

① 이 방향이 맞나?

외부 변수 반영 → 진화

  • 선례 있음: 에너지 가격 시계열을 외부 변수로 dispatching에 반영한 연구 line (Mouzon 2007, Fang 2011, Che 2017 등 — TOU pricing 기반 스케줄링)
  • 우리도 같은 패턴 — 부품 가용·긴급 여부를 외부 시그널로
  • methodological precedent ✓

판단 필요: 이 framing이 충분히 differentiated 한가? 다른 angle은?

② 성능 최적화 더 ↑

현재 결과를 더 강하게

  • multi-urgent S2 강화 → P3 차별성
  • cross-scenario memory bank → P3 효과 증폭
  • longer evolution (50+ iter) + 더 강한 LLM
  • flex sweep 세분화로 sweet spot 정확 위치
  • Brandimarte Mk01~Mk10으로 외부 신뢰성 확보

장점: 현 framing 그대로, 결과 strong하게.
위험: incremental하게 보일 수 있음.

③ 제약조건 현실화

시뮬레이터 자체를 더 현실로

  • Setup time: 작업 전환 시 머신 준비시간
  • 에너지 비용: TOU pricing — 시간대별 변동
  • 머신 고장 + 수리: stochastic breakdown
  • 작업자 가용성: shift 패턴
  • 재공품 (WIP) 한도: 버퍼 제약
  • 이런 제약 추가하면 LLM 우위 영역 확장 가능성

장점: 새 contribution.
위험: scope 확대 → 일정 부담.

핵심 질문: (a) 지금 framing(외부 충격 변수 반영)을 더 깊게 갈 것인가, (b) 제약조건 종류를 늘려 시뮬레이터 현실성으로 differentiation 할 것인가? 둘 다 가능하지만 일정 안에 둘 다는 어려움.
📝 부가 설명 — 세 방향의 trade-off
  • 방향 ①의 학술적 위치: energy-aware FJSSP 문헌 (Mouzon, G. et al. 2007 "Operational methods for minimization of energy consumption of manufacturing equipment"; Fang, K. et al. 2011 "A new approach to scheduling in manufacturing for power consumption and carbon footprint reduction"; Che, A. et al. 2017 "Energy-efficient bi-objective single-machine scheduling")이 외생 시계열 변수를 dispatch 규칙에 반영한 선례. 우리의 part_available_time / urgent_order_flag 외란 변수는 같은 메타-패턴 (exogenous signal in dispatch logic). methodologically 정당화됨.
  • 방향 ②의 risk: 결과를 다듬어도 "incremental"이라는 평가 받을 수 있음. 그러나 multi-urgent 강화로 P3 메모리 효과를 selectively 강화한다면 RQ3의 답이 분명해져 contribution 강화 가능.
  • 방향 ③의 risk: setup time / energy / breakdown 추가하면 scenario 공간이 폭발 (S0/S1/S2 × 새 제약 × 새 파라미터). 일정 안에 cell 수 통제 필수.
  • 레퍼런스 확인 권장: 위 인용 논문 제목은 후보들이며 발표 전 정확한 인용 정보(저자·연도·저널·volume) 검증 필요.
